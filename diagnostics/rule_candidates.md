## Passing controls using the same formats

- In the same evidence_92 JSON format, `account_5334` has a populated nested profile email. Identity resolution links it to user_24, state is PRESENT, and the engine emits the expected report/remediation/verification sequence for case_24.
- In the same evidence_92 analytics collection, `analytics_3697` has a populated email (its customer reference is null). That email links to user_30; parser, identity, state, policy, and planner all receive the record.
- In evidence_94 logs, completed read `analytics_037` has a populated lookup/email for user_50. It is linked and the engine emits the expected analytics finding/remediation/verification. `analytics_9406` has the same format but no identifier value. This indicates the parser and exact matcher work when the source supplies the edge.

These controls differ at the source data: populated identity values are present in passing rows and absent in the five failing records. No parser normalization can recover a value that the record does not contain.

## Candidate experiment

I tested one state-only candidate in memory: classify an `analytics_profile_read_completed` record with a resource ID and nonempty `audience_cohort` as PRESENT. Positive assertion: returned cohort record is PRESENT. Negative assertions: a `_started` event remains unknown, and a capture after `audit_at` remains excluded. All assertions passed.

Across the public 32 samples, the candidate changed **zero predictions** and zero metrics: status 31/32, step count 13/32, aligned fields 1002/1148 (87.28%), exact sequences 13/32, 29 missing resources and one extra. In case_03, the target still fails earlier at identity resolution (`lookup_key=null` and no trace-to-user edge), so state reconstruction, policy and planner cannot use it. The rule is not retained in production.

## Decision

No candidate qualifies as a safe, measurable prediction fix. The concrete missing facts are a subject reference/lookup key for the subjectless evidence_92 rows and a requester identifier on the evidence_94 trace. Resolving them via neighboring rows, resource-ID suffixes, event success, or time proximity would create unsupported identity links. No prediction code or candidate output was changed; no new persistent tests were needed because the in-memory candidate was rejected.
